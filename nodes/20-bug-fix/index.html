Bug集中修复

节点 20 / 57 · 最后修订：2026年5月11日

亲友测完了，反馈堆在共享表里——有的是页面白屏，有的是数字算错，有的是按钮不好点。一个人怎么从一堆Bug中杀出一条路？

一、Bug分类：不是所有Bug都值得你今晚修

四象限法

``

影响大

│

P0 │ P1

"不修会死" │ "不修很痛"

────────────┼────────────

│

P3 │ P2

"修了浪费" │ "修了更好"

│

影响小

`

等级定义OPC处理策略
P0核心流程中断、数据丢失、安全漏洞🔴 立即修，不修不睡觉
P1计算错误、展示异常、逻辑矛盾🟠 当天修
P2体验问题、边界情况🟡 排入本周计划
P3文案错字、对齐偏差🟢 记下来，有时间再说

二、OPC修Bug的三步法

步骤1：复现（5分钟）

一条铁律：你不能在自己电脑上复现的Bug，无法修复。

`

复现步骤模板：

  1. 用什么设备/浏览器/网络？
  2. 从哪个页面进入？
  3. 点了什么？输入了什么？
  4. 期望看到什么？实际看到什么？
`

在Bug表里强制要求复现步骤。缺任意一项的Bug = 标记"无法复现"，先跳过。

步骤2：定位（10分钟）

2026年OPC的定位工具箱：

工具场景一句话用法
Chrome DevTools Console前端报错看红字，复制错误信息搜索
console.trace()不知道哪里触发的在可疑函数第一行加，运行看调用栈
Supabase Logs后端查询慢/报错Dashboard → Database → Logs
git bisect"之前好的，不知道哪次改坏了"git bisect start → git bisect bad → git bisect good <旧版本>

步骤3：修复+验证（15分钟）

`

修复代码 → 本地验证 → 提交前问自己三个问题：

□ 改了这个地方，相关的功能还正常吗？

□ 同样的错误会不会在别的地方也发生？

□ 需要加测试吗？（P0必须加，P2可跳过）

``

三、你不应该修的三类Bug

1. 只有一个人遇到的Bug

20个测试者里只有1个人遇到 → 标记"无法复现"，观察。如果后面又有人遇到再修。

2. "改个设计就好了"的Bug

"这个按钮换个颜色可能更好看" → 不是Bug，是需求。记下来，排到下个迭代。

3. 修一个Bug引入三个新Bug的风险型

有些Bug的根因牵连太广，你评估后觉得"修了可能地震" → 记录下来，等有3个同类问题一起重构。

四、修Bug的时间纪律

时段做什么
上午9:00-9:30扫描Bug表，标出今天的P0/P1
每修完一个Bug在表里更新状态 + 跑一遍节点18的核心路径
晚上8:00今天的P0必须清零。P1最多剩1个
绝对不要：开发新功能到一半，"顺便"修个Bug —— 上下文切换的成本比你想象的高3倍。

五、检查清单

  • 所有Bug都有复现步骤
  • P0已清零
  • P1不超过2个
  • 每个修复后跑了核心路径回归
  • Bug表状态已更新
