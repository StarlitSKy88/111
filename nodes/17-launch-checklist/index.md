### 概述

网站/产品上线前，最怕的不是没流量，而是带着bug上线、带着合规风险上线。好不容易推广来了第一批用户，结果因为支付报错、页面打不开、或者法律问题把用户吓跑了——第一印象坏了，以后很难挽回。本节点提供一个完整的上线前检查清单，确保你的产品以最好的状态面对用户。

### 详细说明

#### 一、功能检查：确保每个流程都能跑通

**1.1 核心功能测试清单**

| 功能 | 测试要点 | 通过标准 |
|:---|:---|:---|
| 注册/登录 | 正常注册、登录、找回密码、退出 | 所有流程跑通 |
| 主要页面 | 首页、服务介绍、定价、联系页面 | 加载时间<3秒 |
| 核心业务流程 | 从浏览到下单到支付的完整路径 | 无报错 |
| 移动端适配 | 在手机浏览器打开 | 排版正常、功能可用 |

**1.2 测试方法**

**自己测试**：按业务流程走一遍，记录问题。

**邀请用户测试**（优先）：
1. 找3-5个真实用户（朋友、同事）
2. 让他们自己摸索，不要给提示
3. 观察他们在哪里卡住、哪里报错
4. 这些问题就是优先级最高的修复项

**1.3 常见Bug及修复**

| Bug类型 | 典型表现 | 修复优先级 |
|:---|:---|:---:|
| 页面打不开 | 404、500错误 | **P0** 必须修复 |
| 核心流程断裂 | 支付到一半卡住 | **P0** 必须修复 |
| 表单无法提交 | 填写后点提交无反应 | **P0** 必须修复 |
| 图片加载失败 | 部分图片显示红叉 | **P1** 尽快修复 |
| 移动端排版乱 | 在手机上布局错位 | **P1** 尽快修复 |
| 次要功能失效 | 分享按钮无法使用 | **P2** 上线后修复 |

#### 二、支付测试：确保钱能收进来

**2.1 支付全流程测试**

1. **微信支付测试**：用自己的微信账号实际支付1分钱，验证回调是否正常、订单状态是否更新
2. **支付宝测试**：用自己的支付宝账号实际支付，验证同上
3. **对账验证**：检查商户号后台的订单与本地订单是否一致

**2.2 支付异常场景测试**

| 场景 | 用户看到什么 | 系统应该如何处理 |
|:---|:---|:---|
| 支付超时 | 提示超时 | 订单保持"待支付"，不自动取消 |
| 支付失败 | 显示失败原因 | 允许重新支付 |
| 回调失败 | 无提示 | 后台自动重试，最多3次 |
| 重复支付 | 用户付了两次 | 识别并退款 |

**2.3 支付安全检查**

- SSL证书是否有效（浏览器显示锁标志）
- 支付密码/密钥是否正确配置
- 回调URL是否可访问（不允许localhost）
- 是否正确使用了签名验证（防伪造）

#### 三、合规检查：避免上线后被查

**3.1 必检合规项**

| 项目 | 要求 | 违规后果 |
|:---|:---|:---|
| ICP备案 | 网站必须完成ICP备案 | 网站无法访问 |
| SSL证书 | 网站必须使用HTTPS | Chrome显示不安全 |
| 隐私政策 | 收集用户信息必须公示隐私政策 | 被投诉或罚款 |
| 工商年报 | 每年6月30日前完成 | 进入经营异常名单 |

**3.2 内容合规**

- 网站内容是否涉及需要许可的业务（医疗、金融、教育等）？
- 是否有虚假宣传（如"最"、"第一"等绝对化用语）？
- 是否有侵权内容（图片、文章、字体）？

**3.3 消费者权益保护**

- 是否有退款政策？（至少要有明确的退款说明）
- 是否有客服联系方式？（不能只留表单）
- 是否有退订方式？（邮件/短信营销必须有退订链接）

#### 四、性能检查：别让加载速度杀死用户

**4.1 性能基准**

| 指标 | 目标值 | 测量工具 |
|:---|:---|:---|
| 首页加载时间 | <3秒 | Lighthouse |
| 服务器响应时间 | <1秒 | Chrome DevTools |
| 图片加载时间 | <1秒 | PageSpeed Insights |

**4.2 优化措施**

- 图片压缩（使用TinyPNG或ImageOptim）
- 开启Gzip压缩（Nginx配置）
- 启用浏览器缓存（Nginx配置Cache-Control）
- 使用CDN（阿里云CDN或Cloudflare）

#### 五、监控与应急：上线后如何知道网站挂了

**5.1 必做监控**

| 监控项 | 工具 | 说明 |
|:---|:---|:---|
| 网站可用性 | 阿里云监控/UptimeRobot | 每分钟检测，发现挂掉立即告警 |
| 错误日志 | Sentry | 捕获前端和后端错误 |
| 性能监控 | 百度统计/Google Analytics | 了解用户行为和页面性能 |
| 服务器状态 | 云控制台 | CPU、内存、磁盘监控 |

**5.2 应急预案**

发现问题时的处理流程：

1. **发现**：收到告警或用户反馈
2. **确认**：先确认问题是否真实（可能是误报）
3. **通知**：如果有用户受影响，在网站/公众号告知正在修复
4. **排查**：查看日志，找出原因
5. **修复**：尽快修复，最快的方式可能是回滚
6. **复盘**：问题解决后，总结原因并防止再次发生

**回滚机制**：上线前要确保有回滚能力（能一键恢复到上一个稳定版本）。

### 常见问题

**Q1: 上线前需要做什么测试？**

A: 功能测试、支付测试、合规检查、性能测试。上线前至少保证核心流程跑通、没有P0级bug。

**Q2: 支付测试需要实际付钱吗？**

A: 需要，但可以用最小金额（如0.01元）测试。测试支付后记得向平台申请退款。

**Q3: 没有备案可以上线吗？**

A: 不可以。国内服务器必须完成ICP备案才能访问，否则网站会被屏蔽。

**Q4: 发现bug怎么办？**

A: 按优先级处理。P0（页面打不开、核心流程断裂）必须修复才能上线。P1/P2可以上线后修复。

**Q5: 上线后网站挂了怎么办？**

A: 立即通知用户→排查原因→修复或回滚→修复后重新上线→复盘总结。

**Q6: 上线后用户少怎么办？**

A: 先确保产品没问题，再做推广。种子用户期不要急，10-20个高质量用户比100个流失用户更有价值。

**Q7: 上线和正式运营有什么区别？**

A: 上线是网站能访问了，正式运营是持续做推广、收集反馈、优化产品。上线只是第一步。

**Q8: 需要准备服务器应急预案吗？**

A: 需要。包括：服务器挂了怎么办、数据丢了怎么办、被攻击怎么办。至少要能快速回滚到上一个稳定版本。
