# 节点12：核心功能1开发

> **面向OPC**：你已经有了登录系统、数据库。现在要做出产品的第一个核心功能——用户真正会用的那个东西。本章不是教你写代码，是教你跟AI配合的**Vibecoding循环**：一次Prompt → 测试 → 出错 → 修复 → 再测试，直到功能完整可用。

---

## 一、启动前检查清单

在给AI写任何一个字之前，先确认下面5件事：

```
□ 1. 原型的核心页面截图打开了吗？
      → 截图就是你的"需求文档"。不用写PRD。

□ 2. Supabase的表建好了吗？
      → 核心功能1涉及几张表？字段都加了吗？
      → 回顾节点10：每个功能至少对应一张表。

□ 3. RLS策略开了吗？
      → 如果这个功能需要保护用户数据，先配好RLS（见节点11）。

□ 4. 明确"核心功能1"是什么——用一句话能说清楚吗？
      → 好的描述："用户输入一个链接，系统提取关键信息并保存"
      → 不好的描述："做一个内容分析工具"

□ 5. 准备好了一个干净的 git commit 起点吗？
      → git status 看有没有未提交的改动
      → 有的话先 commit（见节点09）
```

**5项全部打勾 → 开始写Prompt。**

```

【本月要开发的功能】

【边界情况】（告诉AI要考虑的特殊场景）

- 网络断掉时怎么提示？
- 用户连续点击按钮怎么防抖？

【代码规范】
- 单文件 index.html

```

### 使用技巧

**一次只做一个功能。** 不要在一段Prompt里塞两个功能——AI容易搞混，出错后你也不知道是哪部分出的问题。

## 三、Vibecoding循环：OPC的开发节奏

### 什么是Vibecoding

> **Vibecoding = 你描述需求 → AI生成代码 → 你测试 → 发现不对 → 描述问题 → AI修复 → 你重新测试 → 直到对为止。**

你不是在"调试代码"。你是在"调试AI的理解"。这个心态转变很重要。

### 标准循环流程

```
┌─────────────────────────────────────────────┐
│               Vibecoding 循环                  │
│                                              │
│  ① 写Prompt ──→ ② AI生成代码                 │
│       ↑                            │         │
│       │                            ↓         │
│  ④ 描述差异 ←── ③ 测试发现不对               │
│       │                            │         │
│       └────→ ② AI重新生成 ──→ ③ 测试         │
│                                              │
│  结束条件：③ 测试全部通过 → git commit        │
│                                              │
│  熔断条件：连续5轮还是不对 → 换个更小的目标    │
└─────────────────────────────────────────────┘
```

### 循环四步详解

#### ① 写Prompt

把第二节的模板填好，发给AI。**关键**：一次只说一个功能。

#### ② AI生成代码

AI给你返回代码。你需要做的事（按此顺序）：
1. 复制AI生成的完整HTML代码
2. 粘贴到你的 `index.html` 中，替换全部内容（`Ctrl/⌘ + A` → 粘贴 → `Ctrl/⌘ + S` 保存）
3. 刷新浏览器

#### ③ 测试

在浏览器里，假装你是一个第一次用这个产品的用户：

| 测试什么 | 怎么测 |
|---|---|
| 页面正常打开了吗？ | 刷新浏览器，看有没有白屏 |
| 样式对吗？ | 深色背景？按钮颜色对？布局没歪？ |
| 核心功能走通了吗？ | 按原型流程完整走一遍 |
| 边界情况呢？ | 输入框留空直接点提交 → 有提示吗？ |
| 手机端呢？ | 打开浏览器的手机模拟模式（F12 → 手机图标）|

**关键**：用控制台看有没有报错。

- Chrome：`F12` → Console 标签页
- 红色文字 = 错误。**截图保存。**
- 黄色文字 = 警告。可以暂时忽略。

#### ④ 描述差异

当测试发现不对时，**不要自己去改代码**。把问题描述清楚发回给AI：

```
测试发现问题：

1. [具体问题描述]
   期望：[应该是什么样的]
   实际：[现在是什么样的]
   复现步骤：[怎么操作能触发这个问题]

2. [第二个问题]
   ...

3. 控制台报错截图：
   [粘贴截图]

请修复以上问题，只改相关部分，保持其他功能不变。
```

**描述问题的黄金法则**：
- ❌ "按钮坏了" → AI不知道怎么修
- ✅ "点击'保存'按钮后，页面没反应，控制台显示 'saveMessage is not defined'"

### 熔断机制：什么时候停下来换个方法

连续5轮修复后功能还是不对 → 不要继续发同一个Prompt。

换个策略：
1. **缩小目标**："先只做功能的第一小步——只做输入框+按钮，先不管结果展示"
2. **换种描述**：用完全不同的语言重新描述功能
3. **把问题拆开**："按钮点不动"和"数据没保存"是两个问题，分开报

## 四、常见踩坑及标准修复Prompt

### 坑1：AI忘了引入Supabase SDK

**症状**：控制台报 `supabase is not defined` 或 `createClient is not defined`

**修复Prompt**：
```
请在index.html的<head>标签内加入Supabase CDN引用：

<script type="importmap">
{
  "imports": {
    "@supabase/supabase-js": "https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2/+esm"
  }
}
</script>

然后用 import { createClient } from '@supabase/supabase-js' 方式引入。
```

### 坑2：样式丢失

**症状**：刷新后页面布局乱了、颜色不对、元素堆在一起

**修复Prompt**：
```
样式丢失了。请检查是否有以下问题：
1. <style>标签是否在<head>内？
2. CSS选择器是否和之前一致？
3. 是否有重复的CSS规则互相覆盖？

只检查样式部分，不要改功能代码。
```

### 坑3：Supabase操作中user_id没填

**症状**：插入数据时报错，或数据插入成功但查不出来

**修复Prompt**：
```
现在messages表有user_id字段，所有插入操作需要带上当前登录用户的ID。

请修改所有 supabase.from('messages').insert() 调用，加上：
user_id: (await supabase.auth.getUser()).data.user.id

同时修改所有 .select() 调用，加上过滤条件只查当前用户的数据。
```

### 坑4：AI一次改了太多，把之前好的功能改坏了

**症状**：修了一个小bug，结果登录功能不工作了

**修复Prompt**：
```
之前的功能被你的修改影响了。请恢复到上一版，只修改我指定的这一个问题：
[具体问题]

其他所有功能（登录、消息列表等）保持不动。
```

### 防坑策略

> **每改完一个功能就 git commit。** 这样即使AI改坏了，你可以 `git checkout -- index.html` 瞬间恢复。

## 五、功能完成标志

### 判断标准（必须全部通过）

```
□ 1. 一个完全不懂你的产品的朋友，能在不问你任何问题的情况下，独立走完核心功能
□ 2. 在手机端操作一遍，没有任何按钮点不到
□ 3. 控制台（F12 → Console）没有任何红色错误
□ 4. 输入框留空点提交，有中文提示（不是英文报错）
□ 5. 断网状态下点击按钮，有"网络异常，请检查连接"的提示
□ 6. 连着操作10次，功能正常不出错
```

**6项全部通过 → 功能1完成。**

## 六、git commit 规范

### 功能完成后提交

```bash
git add .
git commit -m "✅ 完成核心功能1：[功能名称]
- 实现[功能要点1]
- 实现[功能要点2]
- 修复[数量]个边界情况
- 移动端适配完成"
git push
```

### 每个功能一个commit

不只是为了记录——以后如果核心功能2的开发弄乱了核心功能1的代码，你可以精确回到"功能1完成时"的那个版本。

## 总纲

> Vibecoding循环是你作为OPC的核心工作节奏。它不需要你会写代码——但需要你**会描述问题**。

**OPC开发节奏**：
```
周一上午：写好Prompt → AI生成
周一下午：测试 → 发现问题 → 描述差异
周二上午：AI修复 → 重新测试
周二下午：功能通过 → git commit
周三：启动核心功能2
```
