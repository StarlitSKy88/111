# 节点18：开发者自测流程

> **面向OPC**：你没有人帮你测。没有QA、没有测试工程师、没有同事帮你点两下。你是写代码的人，你也是唯一负责质量的人。本节点告诉你：一个人怎么测出一个团队的信心。

---

## 一、OPC自测的第一原理

### 残酷真相

大公司的QA团队 = 你的"睡前30分钟"。你没有更多时间了。

**所以OPC的自测不是"测全"，而是"测死"——只测会死人的。**

### 什么是"会死人的"？

| 优先级 | 定义 | 举例 |
|---|---|---|
| 🔴 P0 | 用户的核心流程断了 | 支付后订单没创建、登录后白屏、注册收不到验证码 |
| 🟠 P1 | 核心流程能用但数据错了 | 金额显示少了一个0、统计数据对不上 |
| 🟡 P2 | 功能正常但体验糟糕 | 按钮点了没反应（但刷新后好了）、图片加载慢 |
| 🟢 P3 | 不影响使用的瑕疵 | 文案有个错别字、对齐有点歪 |

**OPC铁律：上线前P0/P1必须清零。P2可以上线后修，P3可以不管。**

## 二、OPC自测五步法（每天30分钟）

### 步骤1：核心路径走查（10分钟）

打开一个全新的无痕浏览器窗口（模拟新用户），从头到尾走一遍你的产品核心路径：

```
打开首页 → 注册 → 登录 → 核心功能1 → 核心功能2 → 核心功能3 → 支付 → 退出 → 重新登录
```

**检查点**：
- 每一步的页面是否正常打开（不是白屏）
- 每一步的按钮是否可点击（不是灰色的）
- 数据是否有留存（退出重新登录后数据还在）

**用一个清单，每天勾一遍：**

```
□ 新用户注册成功
□ 登录正常（账号密码 / 验证码）
□ 核心功能1完整走通
□ 核心功能2数据正确展示
□ 核心功能3正常触发
□ 支付流程到确认页（不实际付款）
□ 退出后重新登录数据还在
□ 手机端同样流程走一遍
```

### 步骤2：边界值爆破（5分钟）

核心功能里所有有"输入"的地方，用以下值逐个测试：

| 输入类型 | 测试值 |
|---|---|
| 空值 | 什么都不填直接提交 |
| 超长 | 复制一篇5000字文章粘贴进去 |
| 特殊字符 | `<script>alert(1)</script>` / emoji / 零宽字符 |
| 负数 | 金额输入 -100 |
| 超大数 | 金额输入 9999999999 |
| 手机端 | 在手机上重复以上测试 |

**如果有一个地方崩溃了，这就是今天的P0 Bug。**

### 步骤3：网络异常模拟（3分钟）

打开浏览器开发者工具（F12）→ Network → 选"Offline"或"Slow 3G"：

```
□ 断网状态下打开页面（是否有提示，而不是白屏）
□ 慢网速下核心功能能否在10秒内完成
□ 支付过程中断网（订单状态是否正确）
□ 提交表单时断网（数据是否丢失）
```

**2026年新增关注**：中国移动/联通/电信的4G网络在某些区域实际速度只有500KB/s。用Slow 3G模拟就是真实用户的体验。

### 步骤4：浏览器兼容（2分钟）

OPC产品的用户大概率用这些：

| 环境 | 必测原因 |
|---|---|
| 微信内置浏览器 | 国内50%以上的Web流量来自微信内打开 |
| Safari (iOS) | iPhone用户在微信里点链接，最终打开的是Safari内核 |
| Chrome (桌面) | 你开发用的浏览器，自测默认环境 |

**不需要测**：Firefox、Edge、三星浏览器（市场份额都<3%）。

### 步骤5：数据一致性检查（5分钟）

打开数据库，做以下检查：

```sql
-- 1. 有没有孤儿数据（引用了不存在的用户/订单）
SELECT * FROM orders WHERE user_id NOT IN (SELECT id FROM users);

-- 2. 有没有重复数据（同一个业务实体存了两份）
SELECT email, COUNT(*) FROM users GROUP BY email HAVING COUNT(*) > 1;

-- 3. 时间戳是否合理
SELECT * FROM orders WHERE created_at > NOW();  -- 未来时间的订单
SELECT * FROM orders WHERE created_at < '2024-01-01';  -- 时间戳明显错误的
```

## 三、2026年OPC可用的自动化测试工具

### 必学：API测试用 Postman / Bruno

```javascript
// 把核心API的测试保存为Collection，每次改完代码点一下"Run"
// Postman Collection: 注册 → 登录 → 创建订单 → 查询订单
pm.test("注册成功", () => pm.response.to.have.status(201));
pm.test("返回了token", () => pm.response.json().token.length > 0);
```

**Bruno 是2026年崛起的开源替代品**（GitHub 25k+星标）。离线可用、测试文件存Git、不强制注册账号。比Postman更适合OPC。

### 可选：前端E2E测试用 Playwright

```javascript
// 5行代码测试核心流程
const { test } = require('@playwright/test');
test('新用户注册到核心功能1', async ({ page }) => {
  await page.goto('http://localhost:3000');
  await page.click('text=注册');
  await page.fill('[name=email]', 'test@opc.test');
  await page.click('text=提交');
  await page.waitForURL('**/dashboard'); // 注册成功应跳转
});
```

**Playwright 2026年优势**：
- 一个命令录制操作生成测试代码：`npx playwright codegen http://localhost:3000`
- 自动等待（不用写sleep），测试稳定不flaky
- 支持微信内置浏览器的User-Agent模拟

**但说实话**：如果你只有一个人，先把P0手动测试跑通，Playwright可以等你有收入后再补。

### 可选：后端单元测试用 Vitest

```javascript
// 测试支付金额计算逻辑
import { describe, it, expect } from 'vitest';
describe('calculateAmount', () => {
  it('会员价格应为9999分', () => {
    expect(calculateAmount('membership')).toBe(9999);
  });
  it('无效productId应抛出错误', () => {
    expect(() => calculateAmount('invalid')).toThrow();
  });
});
```

## 四、自测的时间分配公式

```
每个功能开发完成后：
  15分钟 手动走核心路径  (步骤1)
   5分钟 边界值爆破        (步骤2)
   3分钟 网络异常模拟      (步骤3)
   2分钟 浏览器兼容        (步骤4)
   5分钟 数据一致性检查    (步骤5)
─────────────────────────
  30分钟 / 每个功能
```

**如果30分钟不够** → 说明这个功能太复杂了，拆成两个功能分别上线。

## 五、OPC自测防翻车清单

| 翻车方式 | 预防 |
|---|---|
| **在自己浏览器测完就上线** | 必须用全新无痕窗口测一遍（清掉所有缓存和登录态） |
| **只在桌面测** | 上线前手机微信打开走一遍完整流程 |
| **回调只在本地测** | 支付回调、OAuth回调必须在公网可访问的环境测一次（用ngrok） |
| **改了A功能不测B功能** | 回归测试：改了支付的代码，重新走一遍注册→登录→功能1的流程 |
| **"我就改了一行CSS"** | 改了一行也要走P0核心路径。CSS可能导致按钮错位、文字消失 |

---

## 六、自测通过标准（发布前）

```
□ P0核心路径在无痕窗口通过
□ P0核心路径在手机微信内通过
□ 0个P0/P1 Bug
□ 数据库无孤儿数据/重复数据
□ 边界值输入不崩溃（至少有错误提示）
□ 断网情况下有"网络异常"提示（不白屏）
□ 支付回调在公网环境测试通过（至少一次真实支付）
```
