# 节点13：核心功能2开发

> **面向OPC**：核心功能1跑通了，用户说"有用但不够"。现在你要在第一个功能的基础上，做出产品真正的"护城河"。一个人怎么把一个功能做到让人离不开？

---

## 一、先定义：核心功能2到底是什么

核心功能1解决的是"有没有"——用户能用。核心功能2解决的是"好不好"——用户愿意留下来。

### OPC场景下的三层定位

| 产品类型 | 核心功能1（能用） | 核心功能2（好用） | 核心功能2的价值 |
|---|---|---|---|
| **AI工具** | 输入→AI返回结果 | 历史记录、收藏、导出、分享 | 用户不用每次重新输入，形成使用习惯 |
| **SaaS** | 核心业务功能 | 数据面板、报表、趋势分析 | 让用户看到"用了你的工具后我变好了" |
| **内容产品** | 内容浏览 | 个性化推荐、收藏夹、阅读进度 | 用户粘性从"偶尔看看"变成"每天必刷" |
| **电商/服务** | 商品浏览+下单 | 购物车、收藏、浏览历史、相似推荐 | 客单价提升30-50% |

### 一句话决策原则

> **核心功能2 = 让用户看到"用了比不用好"的证据。**

如果用户用完核心功能1就走了，核心功能2的任务就是让他看到数据、看到变化、看到留下来的理由。

---

## 二、OPC的核心功能2开发铁律

### 铁律1：只做一个功能

不是"做两三个小功能凑成核心功能2"，而是**聚焦一个功能做到极致**。对比：

| ❌ 错误做法 | ✅ 正确做法 |
|---|---|
| 同时做"数据面板 + 导出 + 分享" | 只做数据面板，把图表做到一眼看懂 |
| 功能都做了但每个都半成品 | 一个功能完整到用户愿意截图发朋友圈 |

### 铁律2：必须能独立验证价值

核心功能2上线后，你必须能回答这个问题：**"用户打开这个页面的频率是每天几次？"** 如果做不到量化追踪，这个功能就不够核心。

建议在 `data.json` 里为节点13加一个字段：
```json
{
  "metrics": {
    "dailyActiveUsers": 0,
    "featureRetentionRate": 0,
    "avgSessionDuration": 0
  }
}
```

### 铁律3：与核心功能1无缝衔接

核心功能2不是孤立的新页面，而是核心功能1的自然延伸。用户完成核心功能1的操作后，**不需要额外点击就能看到核心功能2的价值**。

**反面案例**：做了一个很好的数据面板，但用户要在菜单里找三层才能打开。正确做法：核心功能1的操作结果页底部直接嵌入核心功能2的关键数据。

## 三、2026年OPC的快速实现路径

### 路径A：如果你用Supabase（推荐）

Supabase的实时订阅功能（Realtime）让数据面板可以直接监听数据库变化：

```javascript
// 2026年 Supabase Realtime v2 API
const channel = supabase
  .channel('user-activity')
  .on('postgres_changes', { event: 'INSERT', schema: 'public', table: 'user_actions' }, 
    (payload) => { updateDashboard(payload.new); }
  )
  .subscribe();
```

**优势**：30行代码实现实时数据面板，不需要WebSocket服务器。

### 路径B：纯前端 + 浏览器本地存储

如果还没接后端，也可以用 `localStorage` 做轻量版：
- 核心功能1的操作记录存本地
- 核心功能2从本地读取做统计展示
- 用户登录后同步到云端

**优势**：零后端依赖，一天完成。用户离线也能看到自己的使用数据。

### 2026年推荐的数据可视化库

| 库 | 大小 | 学习成本 | 最佳场景 |
|---|---|---|---|
| **Chart.js** v5 | 60KB gzip | ⭐ 极低 | 柱状图、折线图、饼图，10分钟上手 |
| **Recharts** | 150KB | ⭐⭐ 低 | React项目，组件式声明，代码可读性高 |
| **ECharts** | 300KB+ | ⭐⭐⭐ 中 | 需要中国地图、热力图等复杂图表 |
| **Observable Plot** | 40KB | ⭐⭐ 低 | 快速探索性数据可视化，几行代码出图 |

**OPC首选**：如果你用原生JS → Chart.js v5。如果你用React → Recharts。不要一上来就选ECharts，"够用"比"强大"重要100倍。

## 四、开发步骤（OPC精简版）

### 步骤1：确定"用户看完会留下来的那个数据"（2小时）

不要闭门造车。打开核心功能1，问自己：
- 用户每次用完，最想知道什么？
- 什么数据能让用户觉得"我在进步/省钱/省时间"？

把答案写成一句话。这句话就是核心功能2的开发目标。

### 步骤2：设计最小可用展示（1小时）

画一个草图（纸笔或Excalidraw），只包含：
- 一个关键数字（大号展示）
- 一个趋势图（过去7天/30天）
- 一个操作入口（"查看更多"）

**不要加筛选器、不要加导出、不要加对比。** 第一版只需要让人看一眼就懂。

### 步骤3：编码实现（1-3天）

- 前端：选一个图表库，复制官方demo改数据源
- 数据：从核心功能1的数据库表直接读（不要新建表）
- 样式：把数字放大到48px以上，好的数据不需要解释

### 步骤4：埋点验证（30分钟）

在核心功能2页面加上一行统计代码：
```javascript
// 记录用户打开次数
fetch('/api/analytics/track', { 
  method: 'POST', 
  body: JSON.stringify({ event: 'feature2_view', node: 13 }) 
});
```

**上线一周后看数据。** 如果 DAU < 核心功能1的30%，说明功能没做对——改。

## 五、常见翻车与预防

| 翻车方式 | 真实后果 | 预防方案 |
|---|---|---|
| **"顺便把导出也做了"** | 多花3天做导出，数据面板只用了1天，两个都半成品 | 死死守住在步骤2画的那个草图，多一行代码都不要写 |
| **选错图表类型** | 用饼图展示趋势，用户看不懂 | 对照节点14的图表选择指南 |
| **数据太慢** | 核心功能2页面加载5秒，用户直接关掉 | 首屏只加载最近7天数据，历史数据懒加载 |
| **忘了移动端** | 桌面看很好看，手机上图表挤成一团 | Chart.js默认响应式；Recharts加`responsiveContainer` |
